01

O que o sistema resolve

Um controle de qualidade de fones de ouvido, do cadastro do produto ao reteste depois da manutenção. O fone é a entidade central; tudo gira ao redor do histórico dele.

Problema de negócio

Rastrear cada unidade produzida.

Sem um registro único, uma falha de áudio pode ser tratada três vezes, um fone pode ser aprovado sem teste e um lote inteiro perde rastreabilidade. O sistema centraliza cadastro, inspeção, testes técnicos, manutenção e indicadores.

  • Fone: número de série único, modelo, marca, conexão e situação atual.
  • Inspeção: laudo final com inspetor, data, resultado e observação.
  • Testes: evidências técnicas vinculadas a uma inspeção.
  • Manutenção: fila de reparo e liberação para reteste.

O ciclo do fone

Quatro estados e um caminho de volta.

Cadastro

O fone nasce como Aguardando inspeção.

Inspeção

O inspetor aprova ou reprova. O status do fone é atualizado na mesma requisição.

Manutenção

Uma reprovação abre uma ordem de serviço automaticamente. O técnico repara e marca como concluída.

Reteste

O fone vai para Em Análise e volta para a qualidade. O histórico inteiro permanece ligado ao mesmo id_fone.

Em uma frase

O frontend é um conjunto de páginas estáticas em HTML/CSS/JS; o backend é uma API Express que fala PostgreSQL via pg e, se não houver banco, simula as consultas em um arquivo JSON local.

02

Arquitetura em uma olhada

Não existe framework no frontend, nem ORM no backend. O caminho é direto: navegador → Express → SQL → banco ou fallback JSON.

Navegador HTML semântico, CSS por tokens e módulos ES. localStorage
→
Express 5 CORS, JSON, estáticos em dev e 7 grupos de rotas. /api/*
→
Middlewares JWT, cargo normalizado e validação do parâmetro ID. Bearer token
→
Controllers Regras de qualidade, manutenção e CRUD. req / res
→
database.js Adapter ? → $n, Pool PostgreSQL e fallback. pg.Pool
→
Dados Supabase/PostgreSQL em produção ou JSON local. 5 tabelas
O adaptador é uma ponte, não um ORM

O código foi escrito originalmente para MySQL e mantém o formato de retorno do mysql2: [rows, fields]. O adapter traduz ? para $1, $2… e transforma rowCount em affectedRows. Toda query nova precisa respeitar esse contrato.

03

O caminho completo de um fone

Oito passos entre o login e o dashboard. Os callouts vermelhos e amarelos marcam onde o comportamento atual ainda diverge da intenção do produto.

Login e emissão do JWT

POST /api/auth/login procura o funcionário por e-mail, compara a senha (bcrypt ou texto plano legado) e assina um token de 8 horas com id e cargo.

Sessão no navegador

O token e o objeto usuario são salvos em localStorage["sxq_session"]. Cada página chama guardPagina() antes de montar a interface.

Cadastro do fone

O inspetor cria o item. O backend valida série e modelo, aplica os defaults e responde com o id_fone gerado.

Inspeção

O formulário escolhe o fone e o parecer. O id_funcionario não vem do formulário: vem de req.usuarioId, extraído do JWT.

Atualização do status

Uma aprovação deixa o fone Aprovado; uma reprovação deixa Reprovado / Manutenção. Em seguida, o sistema tenta abrir uma OS.

Testes técnicos

O inspetor registra testes ligados à inspeção (áudio, Bluetooth, microfone, bateria). Eles são evidências; não alteram automaticamente o parecer final.

Fila de manutenção

O técnico vê apenas ordens com status diferente de Concluido, descreve a ação corretiva e, ao concluir, o fone vai para Em Análise.

Reteste e dashboard

O fone volta para a inspeção. O dashboard recalcula totais e taxa a cada leitura de /api/inspecoes/dashboard — hoje contando laudos, não fones distintos (ver Diagnóstico).

A OS pode duplicar

Na criação de uma inspeção reprovada, o controller insere uma ordem sem antes verificar se já existe uma aberta. Repetir a reprovação do mesmo fone cria várias OS. Ao aprovar, a OS existente também não é encerrada.

Sem transação no fluxo de inspeção

São várias escritas encadeadas: inserir inspeção, inserir cada teste do checklist, atualizar o fone e abrir a manutenção. Se uma etapa falhar, as anteriores permanecem. O certo é executar tudo em uma única transação.

O que funciona bem

As consultas são parametrizadas, o vínculo inspeção → testes usa ON DELETE CASCADE, o ID do inspetor vem do token e o status do fone é atualizado pelo servidor, não pelo cliente.

01

O modelo em cinco tabelas

O schema está em backend/database.sql. É um modelo enxuto, com chaves seriais, poucas restrições e cascatas que fazem a limpeza do histórico.

Relações do modelo

Quatro ligações, dois comportamentos de exclusão.

  • funcionario 1:N inspecao — ON DELETE SET NULL. Excluir um usuário preserva o laudo, mas apaga o vínculo com o inspetor.
  • fone 1:N inspecao — ON DELETE CASCADE. Excluir o fone apaga todas as inspeções dele.
  • inspecao 1:N teste — ON DELETE CASCADE. Excluir uma inspeção apaga os testes vinculados.
  • fone 1:N manutencao — ON DELETE CASCADE. Excluir o fone apaga as ordens de serviço.
Não existe vínculo inspeção → manutenção

A OS é ligada apenas ao fone. Isso torna impossível saber qual reprovação gerou qual ordem, qual técnico reparou qual laudo e se o reteste aprovou o mesmo defeito. Para rastreabilidade completa, faltaria uma coluna id_inspecao em manutencao (ou uma tabela de eventos).

Integridade, cascatas e estados

O banco protege o que é declarado. O que não é declarado fica por conta do JavaScript — e essa é a maior fonte de inconsistência.

O que o schema garante

Restrições declaradas no DDL.

  • Chaves primárias em todas as tabelas.
  • numero_serie, email e cpf únicos.
  • Campos essenciais com NOT NULL.
  • Integridade referencial em inspeção, teste e manutenção.
  • CHECK de status apenas em manutencao.
  • Cascata limpa o histórico ao excluir um fone ou uma inspeção.

O que fica sem proteção

Regras que só existem no controller.

  • Status do fone pode ser qualquer texto.
  • Resultado da inspeção e do teste não têm CHECK.
  • Não há garantia de uma única OS aberta por fone.
  • Não há vínculo entre OS e inspeção de origem.
  • Não há transação no fluxo de inspeção.
  • Não há created_at / updated_at nem auditoria.

O adaptador PostgreSQL

O projeto nasceu com SQL estilo MySQL. Em vez de reescrever todos os controllers, criou uma camada que preserva o contrato antigo.

O pg retorna um objeto { rows, rowCount }; o código espera [rows, fields]. O adapter faz três traduções:

  • Placeholders: cada ? vira $1, $2… na ordem.
  • INSERT: se a query começa com insert e retorna uma coluna id_*, o valor vira insertId.
  • UPDATE / DELETE: rowCount vira affectedRows.
Toda query de INSERT precisa de RETURNING

Sem RETURNING id_*, o adapter não consegue preencher insertId. As queries atuais incluem RETURNING; mantenha esse padrão ao criar novas rotas.

backend/src/config/database.js
const pool = new Pool({
  connectionString: process.env.DATABASE_URL,
  ssl: { rejectUnauthorized: false }
});

async function pgQuery(sql, params = []) {
  let i = 0;
  const pgSql = sql.replace(/\?/g, () => `$${++i}`);

  const result = await pool.query(pgSql, params);
  const lower = sql.trim().toLowerCase();

  if (lower.startsWith('insert') && result.rows.length) {
    const row = result.rows[0];
    const idKey = Object.keys(row).find(k => k.startsWith('id_'));
    return [{
      insertId: idKey ? row[idKey] : null,
      affectedRows: result.rowCount
    }, []];
  }

  if (lower.startsWith('update') || lower.startsWith('delete')) {
    return [{ affectedRows: result.rowCount }, []];
  }

  return [result.rows || [], []];
}
O contrato é [rows, fields] — e a alteração de senha já o respeita

Todo consumidor precisa desestruturar o retorno: const [rows] = await db.query(...). O userAuthController agora usa db.query com funcionario e id_funcionario, compara a senha atual e grava um hash bcrypt. A única diferença de contrato é a chave da resposta: ele devolve { message }, enquanto o restante da API devolve { mensagem }.

O fallback JSON

Quando não há banco configurado, um provedor local interpreta as consultas mais usadas e grava tudo em local_data.json.

Como ele decide

Três gatilhos de ativação.

  • Não existe DATABASE_URL no ambiente.
  • A conexão inicial com o pool falha.
  • Uma query posterior falha com erro de rede reconhecido (ECONNREFUSED, ENOTFOUND, timeout etc.).

Erros de SQL (tabela inexistente, constraint, sintaxe) não ativam o fallback: eles sobem para o controller. O fallback não é uma recuperação de desastre; é um modo de demonstração.

Limites importantes

Não trate como banco de produção.

  • Reescreve o arquivo inteiro a cada escrita; não há transações.
  • Não há controle de concorrência entre requisições.
  • Consultas não mapeadas retornam [] com um aviso no console.
  • No Vercel, o arquivo fica em /tmp e pode desaparecer.
  • O reset administrativo só afeta esse JSON, nunca o PostgreSQL.

02

O pipeline do app.js

Toda requisição atravessa a mesma sequência. A posição de cada middleware explica vários comportamentos que parecem bugs de frontend.

CORS

Valida a origem antes de qualquer rota. Requisições sem Origin passam; Netlify, Vercel, localhost e a FRONTEND_URL exata são aceitos. Em desenvolvimento, qualquer origem também passa.

Preflight

Um middleware manual responde OPTIONS com 204 e os métodos permitidos, refletindo a origem recebida.

JSON

express.json() transforma o corpo em req.body. Corpos inválidos caem no tratador de erros.

Estáticos

Somente fora de produção, express.static publica a pasta frontend. É por isso que o próprio servidor entrega as páginas locais.

Rotas

/api/auth, /api/fones, /api/inspecoes, /api/testes, /api/manutencao, /api/users, /api/user-auth e o reset administrativo.

Fallback

Rota inexistente cai no 404 padrão do Express, em HTML. O tratador final cobre exceções, devolve { erro, mensagem } e não derruba o processo.

03

Os três middlewares

Autenticação, autorização e validação de ID. São poucos arquivos, mas concentram as regras mais sensíveis do sistema.

authMiddleware

Quem é você?

Lê Authorization, exige o formato Bearer token, verifica com JWT_SECRET e grava req.usuarioId e req.usuarioCargo.

  • Token ausente ou malformado: 401.
  • Assinatura inválida ou expirada: 401.
  • Token válido por 8 horas, sem refresh.

roleMiddleware

O que você pode?

Normaliza o cargo com toLowerCase e remoção de acentos; depois compara com a lista permitida. Admin e Gerente têm bypass global, e a comparação usa includes.

  • checkRole('Admin') aceita Gerente.
  • checkRole('Inspetor') aceita Admin/Gerente.
  • Cargos compostos podem casar por substring.

validarIDParam

O ID faz sentido?

Converte req.params.id com parseInt e rejeita NaN. Não valida se o registro existe — isso fica no controller, que responde 404.

  • Aplicado só em rotas com :id.
  • Não é aplicado em :id_inspecao.
  • isNaN/parseInt são permissivos com sufixos.

    .replace(/[\u0300-\u036f]/g, '')

export async function api(path, { method = 'GET', body } = {}) {
  const token = getToken();
  const opcoes = {
    method,
    headers: { 'Content-Type': 'application/json' }
  };

  if (token) opcoes.headers.Authorization = `Bearer ${token}`;
  if (body !== undefined) opcoes.body = JSON.stringify(body);

  const resposta = await fetch(`${API_URL}${path}`, opcoes);

  if (resposta.status === 401) {
    localStorage.removeItem(SESSION_KEY);
    window.location.href = 'index.html';
    throw new Error('Sessão expirada. Faça login novamente.');
  }

  if (resposta.status === 403) {
    window.location.href = 'acesso-negado.html';
    throw new Error('Acesso negado.');
  }

  const dados = await resposta.json().catch(() => ({}));
  if (!resposta.ok) throw new Error(dados.mensagem || 'Erro na requisição.');
  return dados;
}

04

O ciclo de sessão

Não há cookies, refresh token nem validação local de expiração. A sessão é um objeto no localStorage e a API é a única juíza do token.

1. Login

loginRequisicao chama POST /api/auth/login. A resposta traz token e usuario.

2. Persistência

setSessao grava o JSON em sxq_session. O token fica acessível a qualquer script da origem.

3. Redirecionamento

paginaInicialPorCargo manda Técnico para manutenção, Inspetor para inspeções e os demais para o dashboard.

4. Guarda

guardPagina verifica o token e, se houver lista, o cargo. Admin/Gerente passam por qualquer lista; os outros comparam o cargo normalizado.

5. Shell

initShell injeta sidebar e topbar, filtra o menu e liga os controles responsivos.

6. Expiração

O primeiro 401 limpa a sessão e volta ao login. Não há timer nem renovação; o JWT dura 8 horas.

export function guardPagina(cargosPermitidos = null) {
  if (!estaAutenticado()) {
    logoutRedireciona();
    return null;
  }

  const usuario = getUsuario();

  // Admin e Gerente ignoram a lista de cargos
  if (cargosPermitidos && !isAdminGerente(usuario.cargo)) {
    const cUser = normalizarCargo(usuario.cargo);
    const permitidos = cargosPermitidos.map(normalizarCargo);
    const autorizado = permitidos.some(
      (p) => cUser === p || cUser.includes(p)
    );

    if (!autorizado) {
      window.location.href = 'acesso-negado.html';
      return null;
    }
  }

  return usuario;
}

Consequência prática

O guard não é uma fronteira de segurança.

Ele melhora a experiência e evita que o usuário veja uma tela vazia. A decisão real precisa estar na API. Hoje, um Gerente autenticado consegue abrir user-cadastro.html direto e usar as rotas de usuário; um Técnico consegue chamar GET /api/fones com o próprio token.

Também não há verificação de assinatura no cliente: um token adulterado só é rejeitado quando chega ao backend.

A identidade em uma regra

“Garet comunica. Muli explica.” O sistema combina calor (creme, laranja, dourado) com precisão técnica (marrom profundo, linhas finas, sombras suaves).

Quente

Não é um dashboard frio.

Fundos creme, sombras com marrom em vez de preto e gradientes de energia lembram o produto físico: som, acabamento, calor. O laranja não é decoração gratuita; ele marca ação e atenção.

Técnico

Precisão sem frieza.

Garet nos títulos, números e rótulos; Muli no corpo. Cantos de 3–16 px, bordas de 1 px e espaçamento em múltiplos de 4 px. Evita-se o “cartão flutuante” em toda parte: nem tudo precisa de sombra.

Legível

Contraste antes de estética.

Texto principal em marrom profundo sobre creme. O laranja é usado como fundo, borda ou destaque; texto pequeno em laranja sobre creme não deve ser a regra. A exceção atual é o botão primário branco sobre laranja, que precisa de ajuste.

Netlify: build do frontend

O Netlify não compila JavaScript. O comando node build.mjs apenas grava a URL da API em js/env-config.js e publica a pasta frontend.

netlify.toml
[build]
  base = "frontend"
  publish = "."
  command = "node build.mjs"

[build.environment]
  NODE_VERSION = "18"

[[redirects]]
  from = "/*"
  to = "/index.html"
  status = 200

[[headers]]
  for = "/*"
  [headers.values]
    X-Frame-Options = "DENY"
    X-Content-Type-Options = "nosniff"
    Referrer-Policy = "strict-origin-when-cross-origin"

# o arquivo real também define Cache-Control para /assets, /css e /js

O que o build injeta

frontend/js/env-config.js

O script lê VITE_API_URL, API_URL, BACKEND_URL e NEXT_PUBLIC_API_URL, nesta ordem. Remove barras finais, garante o sufixo /api e escreve:

js/env-config.js
window.__ENV_API_URL = "https://sua-api.vercel.app/api";

No repositório, o arquivo está com string vazia. Isso é normal: ele é sobrescrito no deploy.

O erro mais comum: VITE_API_URL ausente

Sem a variável, API_URL cai no fallback https://site.netlify.app/api. O redirect SPA devolve o index.html, o api.js detecta text/html e mostra “A API retornou HTML em vez de JSON”. A correção é definir a variável no painel do Netlify e refazer o deploy — variável de ambiente não altera um build já publicado.

Arquivos existentes vencem o redirect

O /* → /index.html só é usado quando não existe arquivo correspondente. Por isso /dashboard.html, /documentacao.html, CSS e imagens são servidos normalmente. Já um caminho inexistente, como /api/fones no domínio do Netlify, recebe HTML — daí a detecção no cliente.

Há dois arquivos equivalentes: um na raiz e outro em backend/. O import correto depende de qual diretório você escolhe como raiz do projeto na Vercel.

{

Configuração na Vercel

Environment Variables

  • DATABASE_URL — connection string do Supabase.
  • JWT_SECRET — obrigatório e forte.
  • FRONTEND_URL — URL exata do Netlify/custom domain.
  • NODE_ENV=production — já vem do vercel.json.
  • Não é necessário PORT: a plataforma injeta.

Se você selecionar a pasta backend como root, use backend/vercel.json e o caminho src/app.js.

Sem DATABASE_URL, o Vercel grava em /tmp

O fallback JSON detecta process.env.VERCEL e usa /tmp/local_data.json. Isso permite demonstrar a API, mas o arquivo é efêmero: pode desaparecer entre cold starts ou instâncias. Nunca trate esse modo como persistência de produção — configure o Supabase.

01

O modelo de confiança atual

A API confia em um JWT assinado, no cargo dentro do token e em uma allowlist de origens. Não há sessão no servidor, revogação, MFA, rate limit ou auditoria. O frontend é apenas uma camada de conveniência.

Autenticação

Bearer JWT, 8 horas

O login devolve um token com { id, cargo }. O middleware verifica a assinatura e injeta req.usuario, req.usuarioId e req.usuarioCargo. Não há refresh token, blacklist ou consulta ao banco a cada requisição.

Autorização

Cargo no token

O cargo é copiado do banco para o token no login. Se um usuário for rebaixado, o token antigo continua com o cargo anterior até expirar. A checagem de rota usa esse valor, sem reler o funcionário.

Sessão no cliente

localStorage

O token fica em sxq_session, acessível a qualquer JavaScript da mesma origem. Isso é simples e sobrevive a recarregamentos, mas transforma qualquer XSS em roubo de sessão.

backend/src/middlewares/authMiddleware.js · verificação
const parts = authHeader.split(' ');
if (parts.length !== 2 || parts[0] !== 'Bearer') {
  return res.status(401).json({ mensagem: 'Formato de token inválido.' });
}

jwt.verify(
  parts[1],
  process.env.JWT_SECRET || 'soundx_secret_key_2026',
  (err, decoded) => {
    if (err) {
      return res.status(401).json({ mensagem: 'Token inválido ou expirado.' });
    }

    req.usuario = { id: decoded.id, cargo: decoded.cargo };
    req.usuarioId = decoded.id;
    req.usuarioCargo = decoded.cargo;
    return next();
  }
);
O segredo de fallback é público

soundx_secret_key_2026 está no código-fonte e é usado quando JWT_SECRET não existe. Qualquer pessoa que leia o repositório pode assinar um token com { id: 3, cargo: 'Admin' } e a API aceitará. Em produção, a ausência do segredo deveria impedir o boot — não criar uma porta dos fundos.

02

Senhas e login

Há dois mundos convivendo: usuários novos com bcrypt e seeds em texto plano. O login e a troca de senha aceitam ambos; o cadastro sempre gera hash.

1. Cadastro

POST /api/users valida cargo, comprimento e duplicidade; gera bcrypt.hash(senha, 10).

2. Login

Busca por e-mail. Se o hash começa com $2a$, $2b$ ou $2y$, compara com bcrypt; caso contrário, faz igualdade de texto.

3. Token

Assina { id, cargo } com 8 horas de validade. Não inclui e-mail, nome ou versão de senha.

4. Troca

POST /api/user-auth/change-password usa o ID do token, exige a senha atual e grava um hash novo com custo 10.

5. Expiração

O cliente não sabe quando o token vence. O próximo 401 limpa a sessão e redireciona para o login.

6. Recuperação

Não existe “esqueci minha senha”, e-mail transacional, MFA ou política de complexidade. A senha mínima é 6 caracteres.

O que está correto

Boas decisões já presentes

  • Novos usuários nunca são gravados em texto plano.
  • A troca de senha exige a senha atual e usa o ID do token, não o corpo.
  • O hash usa custo 10, adequado para o volume atual.
  • O token tem expiração explícita de 8 horas.
  • A listagem de usuários não retorna a coluna senha.
  • Erros de login não retornam o hash nem detalhes internos.

O que precisa mudar

Riscos concretos

  • Seeds com 1234 e CPF/e-mail públicos no README.
  • Login revela se o e-mail existe: “Usuário não encontrado” vs. “Senha incorreta”.
  • Sem rate limit ou atraso progressivo contra força bruta.
  • Trocar a senha não invalida tokens emitidos antes.
  • A resposta de erro do userAuthController inclui error.message.

const checkRole = (...cargosPermitidos) => {

O frontend deve espelhar a mesma política. O guard atual também libera Admin/Gerente para qualquer lista, então os dois lados precisam ser corrigidos juntos.

CORS: exatamente o que passa

A configuração não é um wildcard em produção, mas também não é uma allowlist fechada. Ela combina sufixos de plataforma, substring de localhost e uma URL exata.

backend/src/app.js · regra de origem
if (!origin) return callback(null, true);

if (
  origin.endsWith('.netlify.app') ||
  origin.endsWith('.vercel.app') ||
  origin.includes('localhost') ||
  origin.includes('127.0.0.1')
) {
  return callback(null, true);
}

if (process.env.FRONTEND_URL) {
  const allowed = process.env.FRONTEND_URL
    .trim().replace(/\/+$/, '').toLowerCase();

  if (origin.toLowerCase() === allowed) {
    return callback(null, true);
  }
}

if (process.env.NODE_ENV !== 'production') {
  return callback(null, true);
}

return callback(new Error('Bloqueado pela política CORS'));

Leitura linha a linha

Produção e desenvolvimento

  • Sem Origin: passa. Necessário para Postman e chamadas servidor-a-servidor; não é um controle de navegador.
  • *.netlify.app / *.vercel.app: passa. Qualquer inquilino dessas plataformas pode chamar a API; não é só o seu site.
  • Contém localhost/127.0.0.1: passa, inclusive origens como https://localhost.exemplo.com.
  • FRONTEND_URL: comparação exata, sem barra final, case-insensitive. É o único controle realmente fechado.
  • Fora de produção: qualquer origem passa. Simples para desenvolver, perigoso se NODE_ENV faltar no deploy.
Domínio próprio exige FRONTEND_URL

Se o site for publicado em soundx.com.br, nenhum dos sufixos cobre essa origem. Sem FRONTEND_URL=https://soundx.com.br, o navegador bloqueia as chamadas. Com a variável, funciona. Para múltiplos domínios, o código atual não aceita lista: seria necessário separar por vírgula e testar cada item.

    .split(',')

const corsOptions = {

Consultas que corrigem os indicadores

O dashboard atual mistura “quantidade de inspeções” com “quantidade de fones”. A consulta abaixo escolhe a última inspeção de cada fone e conta uma vez.

PostgreSQL · KPIs por fone
WITH ultima AS (
  SELECT DISTINCT ON (id_fone)
         id_fone,
         resultado_final
    FROM inspecao
   ORDER BY id_fone, data_inspecao DESC, id_inspecao DESC
)
SELECT
  (SELECT COUNT(*) FROM fone) AS total_fones,
  (SELECT COUNT(*) FROM inspecao) AS total_inspecoes,
  COUNT(*) FILTER (WHERE resultado_final = 'Aprovado') AS fones_aprovados,
  COUNT(*) FILTER (WHERE resultado_final != 'Aprovado') AS fones_reprovados,
  ROUND(
    100.0 * COUNT(*) FILTER (WHERE resultado_final = 'Aprovado')
    / NULLIF(COUNT(*), 0),
    2
  ) AS taxa_aprovacao
FROM ultima;
Defina a métrica antes de escolher a query

“Fones aprovados” pode significar (a) o status atual em fone.status, (b) a última inspeção de cada fone ou (c) todos os fones que já foram aprovados alguma vez. As três respostas são diferentes. A consulta acima usa (b), que é estável mesmo se fone.status ficar dessincronizado. Se a regra de negócio for (a), use GROUP BY status em fone.

Fórmula atual

O que o endpoint faz hoje

aprovados = COUNT(*) WHERE resultado = 'Aprovado' e total = COUNT(*) em inspecao. A taxa é aprovados / total de inspeções. Isso responde “qual fração dos laudos foi aprovada”, não “qual fração dos fones está aprovada”.

Exemplo que expõe o erro

Um fone, três laudos

Fone X: reprovado, reprovado, aprovado. O painel mostra 3 inspeções, 1 aprovação e 2 reprovações, mas existe apenas 1 fone — e ele está aprovado. A taxa por laudo pode ser útil, mas precisa de outro rótulo.

Transação e reconciliação

A criação de inspeção e a atualização de manutenção precisam de tudo-ou-nada. A exclusão precisa reconstruir o estado a partir do que restou.

database.js · withTransaction
async function withTransaction(callback) {
  const client = await pool.connect();

  try {
    await client.query('BEGIN');
    const resultado = await callback(client);
    await client.query('COMMIT');
    return resultado;
  } catch (error) {
    await client.query('ROLLBACK');
    throw error;
  } finally {
    client.release();
  }
}

// o callback recebe um adaptador com query(sql, params)
// e usa tx.query no lugar de db.query

O que entra na transação

Ordem da criação

  1. Travar o fone e conferir se existe.
  2. Inserir a inspeção e obter o ID.
  3. Inserir os quatro testes.
  4. Atualizar o status do fone.
  5. Garantir uma OS aberta se reprovado; fechar se aprovado.
  6. Commit. Qualquer erro desfaz tudo.

O mesmo vale para concluir manutenção: atualizar a OS e o fone na mesma transação.

Ordem recomendada de correção

Cada etapa deve terminar com o sistema funcionando e testado. Não tente corrigir tudo em um único commit.

1. Fechar a porta

Remover o segredo JWT de fallback, exigir JWT_SECRET, corrigir o CORS para origens exatas e trocar as senhas seed. Sem isso, o resto é discutível.

2. Parar o fallback silencioso

Produção sem banco deve falhar com 503, não gravar em JSON. Expor o provedor ativo em /api/status.

3. Corrigir o RBAC

Remover o bypass global, decidir Gerente por rota, alinhar o guardPagina e testar as 23 operações com cada cargo.

4. Adicionar transações

Começar pela criação de inspeção e pela atualização de manutenção. Só depois mexer nas regras de OS.

5. Impôr a invariante de OS

Limpar duplicatas existentes, criar o índice único parcial e implementar abrir/fechar de forma idempotente.

6. Reconciliar exclusão e edição

Excluir laudo recalcula status; editar decide se o laudo é imutável ou se atualiza foto/testes junto.

7. Corrigir métricas e datas

Dashboard por último fone; formatar DATE sem UTC; migrar timestamps para TIMESTAMPTZ.

8. Fechar o polimento

Tabela de usuários, variável de transição, CSV, popup do laudo, timeout de API e mensagens de login.

Não crie o índice único antes de limpar a fila

Se já existem duas OS abertas para o mesmo fone, o CREATE UNIQUE INDEX falha. Escolha a OS correta, conclua ou exclua as duplicadas e só então crie a restrição. Faça backup antes.
